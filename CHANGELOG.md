# Changelog

The packages built from this repository share one version: `react-native-alpha-video` and `alpha-video-web` on npm, `dev.mediacache:alpha-video` on Maven Central, and the `AlphaVideo` Swift package and `alpha-video` pod.

## 1.0.0 - Unreleased

First public release.

- Plays single-stream VP9 WebM with alpha (YUVA) on Android, iOS and the web. On Android and iOS a C++ core demuxes with libwebm's parser and decodes with libvpx 1.14.0 (VP9, with row multithreading) and dav1d 1.5.1 (AV1), without FFmpeg; the web decodes in WebAssembly with FFmpeg 6.1 and dav1d. iOS renders with Metal, Android with OpenGL ES on a `TextureView`.
- On Android, two MediaCodec decoders decode colour and alpha in hardware, told the clip's colour range and matrix by the same rules as the C++ core. They take dual-stream WebM (colour and alpha in separate VP9 or AV1 tracks), and standard alpha WebM too: the demuxer hands each block's BlockAdditional, a VP9 frame of the alpha, to the second decoder. The view picks the path from the file, and sends it to MediaCodec's software decoders once the hardware decoder hasn't 2 instances free, then to the C++ core. Where the GPU has `GL_EXT_YUV_target`, the shader reads the decoders' raw YUV and converts it with the clip's matrix itself, since drivers can ignore the colour tags of a software decoder's frames (BT.709 AV1 drew as BT.601 on a Snapdragon 778G with `c2.android.av1-dav1d`). Without the extension the driver converts. A VP9 track in a profile no MediaCodec decoder lists (profile 1, which a `gbrp` alpha track encodes to) sends the file to the C++ core instead. Elsewhere the C++ core decodes dual-stream VP9, and dual-stream AV1 on dav1d (8- to 12-bit, drawn at 8 bits), in every playback mode, and expands a limited-range alpha track to the full 0-255. iOS plays dual-stream AV1 this way too. 10-bit VP9 reports `onError` on the C++ core. MediaCodec's software decoders are asked for 8-bit output, since their 10-bit P010 frames drew blank on Adreno.
- The Android `decoder` prop (`setDecoder` on `AlphaVideoView`) forces the engine: `mediacodec` (hardware per track where an instance is free, else software), `mediacodec-hw`, `mediacodec-sw` or `software` (the C++ core). A forced engine reports `onError` rather than fall back. The default, `auto`, takes MediaCodec's hardware decoders, else its software ones, else the C++ core. `onLoad` reports the engine and decoders used, e.g. `mediacodec-hw (c2.qti.vp9.decoder)` or `software (dav1d)`. iOS and the web accept the prop.
- Colour is converted with the clip's range and matrix (limited or full; BT.601, BT.709 or BT.2020), matching FFmpeg's own conversion. An untagged clip is taken as limited range, BT.601 up to 720x576 and BT.709 above. Odd frame sizes keep their last chroma column and row.
- Playback modes for the software path: `stream` (the default: decode ahead, bounded cache), `preload` (decode every frame once) and `streamAndPreload`. A global decode queue (`useDecodeQueue`) keeps many players from saturating the CPU.
- Sources: `https://`, `file://`, absolute paths, `asset://` (Android assets, the iOS bundle, the web root), `res/raw` names and `content://` on Android. On Android and iOS, http(s) files are read by range requests as they play, through the C++ reader of [alpha-video-source](https://github.com/MediaCacheDev/alpha-video-source), with `source.headers` sent with every request: the stream modes start with the first frames, a seek fetches the Cues and the cluster it lands in, and a server without range support works too. Between plays the bytes are kept on disk in the app's cache folder (`storage`: `'auto'`, `'disk'`, `'memory'` or `'none'`; `maxStorageBytes`, default 512 MB), partially, so a clip played through plays again offline; `cacheKey` names the stored copy.
- Playback control: `play`, `pause`, `stop`, `seekToFrame` and `seekToTime`, plus `paused`, `autoPlay`, `loop` and `playbackSpeed`. With `autoPlay` off the first frame shows, in every mode. Events: `onLoad` (frames, size and decoder), `onError` and `onEnd`.
- Android decoder status: `getDecoderStatus`, `getDecoderInfo`, `getMaxDecoderInstances` and `getActiveDecoderCount`.
- React Native: `AlphaVideoView` on both the new architecture (a Fabric view, and a TurboModule for the decoder status) and the old one. On react-native-web it plays through `alpha-video-web`, a dependency: `<video>` where the browser keeps the alpha, otherwise WebCodecs or WebAssembly decoding drawn in WebGL2, so the alpha shows in Safari and for dual-stream files too. The `webDecoder` prop forces an engine, and web errors carry a `code`.
- `alpha-video-web` for plain JS/TS and React, from `web/`. Its canvas engines run the C++ core's demuxer (libwebm's parser) in WebAssembly, reading the file by HTTP range requests as it plays through [alpha-video-source](https://github.com/MediaCacheDev/alpha-video-source): playback starts with the first frames, a seek fetches the Cues and the cluster it lands in, and a server without range support works too. Between plays a URL's bytes are kept in OPFS, else IndexedDB (`storage`, default `'auto'`; `maxStorageBytes`, default 512 MB), so a clip played through plays again with no requests. `src` takes a URL (with `headers`), a `Blob`, bytes or a byte source of the app's own; `cacheKey` names the stored copy. The demuxer module is 184 KB (63 KB gzipped).
- Data sources, for apps that fetch, cache or decrypt the bytes themselves: `AlphaVideoDataSource` on Android and iOS, registered by name in `AlphaVideoDataSources` for React Native's `source.dataSource`. `dev.mediacache:alpha-video-media3` adapts a Media3 `DataSource.Factory` (OkHttp, Cronet, `CacheDataSource`).
- Standalone Android and iOS libraries.
- MIT. The native libraries bundle libwebm's parser and libvpx (BSD-3-Clause) and dav1d (BSD-2-Clause); `alpha-video-web` bundles libwebm's parser, FFmpeg's VP9 decoder (LGPL-2.1-or-later) and dav1d. Their notices are in `THIRD_PARTY_NOTICES.md` and `web/THIRD_PARTY_NOTICES.md`.
- Android libraries are linked for 16 KB pages.
